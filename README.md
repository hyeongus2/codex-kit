# codex-kit

Codex CLI로 몇 시간짜리 업무 과제를 풀 때 쓰는 작업 규칙과 스킬 모음이다. Codex 세션 여러 개와 각 세션의 하위 에이전트가 같은 작업 폴더에서 동시에 나눠 일하도록 짜여 있다. 과제 답, 개인정보, 키는 들어 있지 않다.

## 사용법

과제 README.md가 있는 작업 폴더(예: `~/workspace`)에서 사람이 직접 실행한다. 먼저 `ls`로 README.md가 보이는지 확인한다.

```bash
git clone https://github.com/hyeongus2/codex-kit /tmp/kit
bash /tmp/kit/setup.sh
```

그다음 Codex를 다시 켜고(`/quit` → `codex`) 두 가지를 확인한다.

1. `/skills`에 스킬 6개가 보이는지
2. "역할별로 고칠 수 있는 파일, 커밋하는 명령의 형태, 쓰면 안 되는 git 명령, 검증할 때 확인할 네 가지를 말해"라고 물었을 때 규칙대로 답하는지 (설치된 것과 적용된 것은 다르다)

## 세션 띄우기

세션마다 터미널 하나다. 응시 환경에서 새 터미널을 열고(`+`) 작업 폴더에서 `codex`를 켠 뒤 첫 메시지로 역할을 준다.

| 순서 | 세션 | 첫 메시지 | 언제 |
|---|---|---|---|
| 1 | lead | `역할: lead. ask 세션도 같이 켰어. README 읽고 시작해` | 설치 직후 |
| 2 | ask | `역할: ask. README 읽고 담당자 질문부터 모아` | lead와 같이 바로 |
| 3 | part-<이름> | `역할: part-<이름>. README와 CONTRACT.md 읽고 시작해` | lead가 세션 표와 뼈대를 커밋하고 띄워 달라고 할 때. 이름과 수는 PLAN.md '세션 표'를 따른다 |
| 4 | check | `역할: check. README와 CONTRACT.md 읽고 시작해` | CONTRACT.md가 나온 뒤 |

- lead가 split-parts 스킬로 세션 수와 이름, 각 세션의 첫 메시지를 PLAN.md '세션 표'에 적고 보여 준다. 그대로 붙여 넣으면 된다.
- AGENTS.md는 Codex가 켜질 때 스스로 읽으므로 첫 메시지에 넣지 않아도 된다. 설치 [주의]가 AGENTS.md를 못 읽는다고 했거나, 세션을 켠 뒤 AGENTS.md가 바뀌었으면 "AGENTS.md 읽고 따라"를 덧붙인다. README는 스스로 읽지 않으므로 첫 메시지에 넣는다.
- 세션끼리는 파일로 맞춘다. 각자 `work/<역할>.md` 맨 위 '상태'와 '요청'을 쓰고, 단계마다 남의 상태·요청과 CONTRACT.md '변경 이력'을 읽는다. 기다리던 것이 끝났으면 사람 확인 없이 다음 단계로 간다.
- 쉬고 있는 세션은 파일이 바뀌어도 스스로 알지 못한다. 세션의 마지막 답변 끝에 `전달 → <세션>: "…"` 줄이 있으면 따옴표 안의 말을 그 세션 터미널에 붙여 넣는다. 이 줄이 세션 사이를 잇는다. 세션은 받는 쪽에 할 일이 생겼을 때만 이 줄을 쓴다.
- 전달 줄 붙이는 요령:
  - 받는 세션이 일하는 중이면 응답이 끝난 뒤 붙인다. 일하는 중에 붙이면 하던 응답에 끼어든다.
  - lead가 일하는 중이면 lead 앞 전달은 대부분 건너뛴다. lead는 단계마다 다른 세션의 상태를 스스로 읽는다. lead가 쉬고 있을 때만 하나로 묶어 붙인다.
  - 한 세션에 갈 전달이 여러 개면 한 메시지로 묶는다.
  - 받는 세션이 이미 그 내용을 처리했다고 말했거나, 그 세션 work 파일 '받은 요청 처리'에 이미 적혀 있으면 건너뛴다.
  - 받는 세션을 아직 띄우지 않았으면 그 세션을 띄울 때 첫 메시지 뒤에 덧붙인다.
- 담당자 질문은 각 세션이 자기 work 파일 '질문'에 쓰고 `전달 → ask` 줄을 남긴다. ask가 모아 중복을 빼고 INTERVIEW.md '다음에 보낼 질문 묶음'으로 만든다. 사람은 그 묶음을 담당자에게 보내고 답을 ask 터미널에 붙여 넣는다.
- 세션 표의 역할은 사람이 띄우는 세션이 맡는다. 각 세션은 자기 범위 안에서 오래 걸리고 서로 독립인 일을 하위 에이전트에게 나눠 동시에 돌린다.
- 세션이 기다리는 중이면 무엇을 기다리는지와 끝나면 뭐라고 말하면 되는지를 알려 준다. 그 말을 그 터미널에 넣으면 이어 간다.
- 제출 시작: PLAN.md '시간표'의 제출 시작 시각이 되면 lead 터미널에 `제출 시작 시각이야`를 보낸다. 쉬고 있는 lead는 시각이 돼도 스스로 final-check를 시작하지 못한다. lead가 일하는 중이면 그 응답이 끝난 뒤 보낸다.

설치 출력에 [주의]가 있으면 그 줄을 복사해 lead 첫 메시지에 붙여 넣는다. Codex는 설치 출력을 보지 못한다. lead가 처리해 PLAN.md '기록 위치'에 적으면 다른 세션은 그것을 따른다. AGENTS.md를 못 읽는다는 [주의]면 모든 세션 첫 메시지에 "AGENTS.md 읽고 따라"를 덧붙인다(위). 터미널에서는 텍스트를 선택한 뒤 `Ctrl+C`로 복사하고 `Ctrl+Shift+V`로 붙여 넣는다. 선택 없이 누른 `Ctrl+C`는 실행 중인 명령(Codex 포함)을 멈추므로 조심한다.

승인 창, `/compact`, 추론 강도 같은 조작은 아래 '사람이 Codex에서 하는 조작'을 본다.

스킬은 Codex 표준 위치(`~/.agents/skills`)에 복사한다. 응시 환경이 스킬 적용 방법을 따로 안내하면 그 방법을 따르고, 모르면 Cofa Helper에게 묻는다. 스킬을 쓸 수 없으면 Codex에게 "`/tmp/kit/skills/<이름>/SKILL.md` 읽고 그 절차대로 해"라고 한다.

키트는 MCP를 쓰지 않는다. MCP는 응시 환경의 MCP 탭에서 과제에 필요할 때만 설정할 수 있다.

에디터에 PLAN.md 같은 기록 파일을 열어 둔 채 Codex가 그 파일을 고치면 "외부 변경 감지"가 뜬다. 이때는 "외부 변경 불러오기"를 골라 Codex가 쓴 최신 내용을 가져온다.

Codex에게 설치를 시켜도 되지만, 네트워크 접근과 `~/.agents` 쓰기 때문에 승인 창이 뜬다. 사람이 직접 치는 쪽이 빠르고, 설치 작업이 과제 기록에 섞이지 않는다.

설치가 계속 막히면 오래 붙잡지 말고 키트 없이 진행한다. 짧은 AGENTS.md를 작업 폴더에 직접 쓰면 된다.

## 사람이 Codex에서 하는 조작

사람이 Codex 터미널에서 누르는 키와 명령이다. AI가 화면을 조작하는 Computer Use가 아니다. Computer Use는 공식 금지이고 키트는 쓰지 않는다. 로컬 리허설(Codex CLI 0.163, 작업 공간 쓰기 샌드박스, 필요할 때 승인)에서 확인한 것이며, 응시 환경 화면이 다르면 그쪽을 따른다.

### 승인 창
- `Yes, proceed`(y, 이번만), `don't ask again for commands that start with …`(p), `No`(Esc)가 뜬다. 공식 안내대로 명령을 확인한 뒤 고른다.
- p가 보이면 p를 고른다. 응시 중 Cofa Helper가 눌러도 된다고 답했다(사용자 확인). p가 없으면 y를 고른다. 커밋 승인 창은 y로 충분하다(아래).
- 승인 창이 떠 있는 세션은 사람이 고를 때까지 멈춰 있다. 쉬는 것처럼 보이는 세션이 있으면 승인 창부터 확인한다.
- 샌드박스가 `.git` 쓰기와 로컬 접속(서버 실행, `curl`, HTTP 테스트)을 막으면 그때마다 승인 창이 뜬다. 커밋은 `git add … && git commit … -- …` 한 줄이라 한 번 뜬다.
- p 옆의 접두는 Codex가 제안한다. Codex 0.163 안내문은 비슷한 일을 다시 묻지 않을 만큼 범위를 잡되, `python3`처럼 아무 스크립트나 돌릴 수 있는 접두는 제안하지 말라고 한다. 삭제 명령(`rm`)과 heredoc 명령에는 p가 없다.
- p는 `~/.codex/rules`에 규칙을 저장하고, 그 뒤 세션에도 적용된다. 이미 켜진 다른 세션에 바로 적용되는지는 확인하지 않았다.
- 명령에 `*`, `?`, `>`, `$(…)`, `이름=값`이 들어가면 Codex는 저장된 규칙을 적용하지 않고 승인이 필요할 때마다 다시 묻는다. 그래서 CONTRACT.md의 고정 테스트 명령에는 이 기호를 넣지 않는다.
- 커밋 승인 창의 p 접두는 `git add <그 파일들>`이다. lead·part처럼 커밋마다 파일이 다르면 거의 다시 쓰이지 않으니 y로 충분하다. ask처럼 같은 기록 파일만 커밋하는 세션은 같은 접두(`git add INTERVIEW.md work/ask.md`)가 계속 나온다(검증 리허설 15번). 그 세션은 p가 승인을 줄일 수 있다. `git commit` 쪽까지 덮는지는 p를 눌러 확인하지 않았다.
- 테스트 명령의 p 접두(`python3 -m unittest …`)도 같은 모양으로 10~24번 반복됐다(검증 리허설). 고정 테스트 명령은 p를 고르는 것이 승인을 가장 많이 줄인다.
- 서버를 끄는 승인 창도 뜬다: 실행 중인 서버 터미널에 Ctrl+C를 보내는 `send input to terminal`(p 없음)과 `kill -TERM <번호>`. 그 세션이 자기가 띄운 서버를 끈다는 이유 문장을 보고 고른다. 포트·프로세스 조회(`ss`, `pgrep`)도 샌드박스가 막아 승인 창이 뜬다. 읽기만 하는 명령이다.
- Codex 0.163 권한 메뉴에는 AI 검토자가 승인 요청을 대신 판단하는 'Approve for me'가 있다. 리허설에서 쓰지 않았고 응시 환경에서 허용되는지 모른다. 설정을 바꿔 차단 기능을 우회하는 것은 공식 금지이므로, 쓰려면 먼저 Cofa Helper에게 묻는다.
- Esc(No)를 누르면 그 명령만이 아니라 하던 응답 전체가 멈춘다(`Conversation interrupted`). 거절한 직후 대신 할 일을 입력한다. 예: "INTERVIEW.md는 빼고 네 파일만 커밋해".
- 하위 에이전트가 승인을 기다리면 메인 화면에는 `Approval needed in Agent (…) /subagents` 한 줄만 뜬다. `/subagents`로 그 스레드에 들어가 승인한다. 그 화면에서는 입력이 막히므로 ←(Agent command center)에서 메인 세션을 골라 Enter로 돌아온다.

### 그 밖의 화면
- 업데이트 안내: Codex를 켤 때 업데이트 안내가 먼저 뜨면 건너뛴다(Skip).
- 질문 칸: `Queued follow-up inputs ? 1 question … shift+← to answer` 한 줄이 보이면 Codex가 사람에게 묻고 있는 것이다. 쉬는 것처럼 보여도 답을 기다린다. shift+←로 열어 선택지를 고르거나 답을 쓴다.
  - 선택지의 Other(직접 쓰기)는 고른 뒤 Enter를 먼저 누르면 빈 답이 간다. Other로 옮긴 뒤 바로 답을 붙여 넣고 Enter를 누른다.
  - 질문 칸을 여는 사이 승인 창이 앞에 뜨면 Enter가 승인으로 간다. 화면 맨 아래가 `Press enter to confirm or esc to cancel`이면 승인 창이다. 승인부터 고르고 다시 shift+←로 연다.
  - 선택지 없이 `Type your answer`만 뜨는 질문 칸도 있다. 바로 답을 붙여 넣고 Enter를 누른다.
  - 질문 칸으로 담당자에게 물을 것(업무 규칙, 형식)이나 다른 세션의 일(계약, 전달 부탁)을 물으면 사람이 답을 지어 주지 않는다. `담당자 질문은 work 파일 '질문'에 적어 ask에, 계약은 '요청'에 적어 lead에 전달 줄로 보내`라고 답한다.
- 일하는 중에 보낸 메시지: 응답이 끝난 뒤가 아니라 하던 응답에 바로 들어가 방향을 바꾼다. 방향을 고칠 때 쓰고, 다음 단계 지시는 응답이 끝난 뒤 보낸다.
- Agent command center(←): 열린 세션과 세션별 토큰을 한 화면에서 본다.
- `/compact`: 대화가 길어지면 쓴다(리허설에서 42초). 치기 전에 그 세션에 "곧 /compact 할게. 기록 파일을 최신으로 하고 커밋해"를 보내고, 끝나면 `/compact`를 친다. 역할, 소유 파일, 다음 할 일은 work 파일에 있어 이어진다. 자동 요약은 예고 없이 일어나므로 세션은 단계마다 기록한다.

### 화면 확인
- 세션이 포트와 경로를 알려 주면 플랫폼 Browser 도구에 넣어 본다.
- 화면을 보는 동안 다른 세션은 승인 창에서 멈춰 있을 수 있다. 화면 확인을 시작하기 전과 끝낸 뒤 모든 세션의 승인 창부터 훑는다.
- 본 결과는 확인을 부탁한 세션 한 곳에만 말한다. 문제가 여러 부품에 걸치거나 누구 것인지 모르면 lead에게만 말한다. 두 곳에 말하면 같은 문제를 두 세션이 따로 고친다.
- 파일을 올리는 화면이면 Browser 미리보기에서 작업 공간의 파일을 고를 수 있는지 먼저 해 본다. 안 되면 그 세션에 그렇게 말한다. 리허설에서는 확인하지 못했다.

### 추론 강도
- 세션을 켠 뒤 `/model`에서 모델과 추론 강도를 고른다. 응시 환경 모델이 어느 강도까지 되는지는 그때 본다. 강도가 높을수록 느리고 토큰을 많이 쓴다.
- 강도 화면에서는 `s`를 눌러 이 세션에만 적용한다. Enter는 기본값을 바꿔 그 뒤에 켜는 모든 세션에 적용된다(Codex 0.163 화면: `enter default · s session`).
- lead는 high로 둔다. 부품 나누기, CONTRACT, 통합 판단이 모든 세션에 퍼진다. xhigh는 응답이 느려져 lead를 기다리는 세션이 같이 늦어지므로, 어려운 설계나 안 풀리는 버그 때만 잠깐 올렸다가 내린다.
- part, check, ask는 medium으로 둔다. 계산이나 규칙 판정이 까다로운 부품이거나 같은 테스트가 두 번 이상 실패하면 high로 올린다.

### `/goal`
part·check 세션이 단계 계획을 보여 주고 확인을 기다리면 확인과 목표를 한 번에 준다.

```
/goal 계획 확인했어. work/<역할>.md 단계 1~N을 모두 구현하고, 단계마다 검증을 통과시켜 자기 파일만 지정해 커밋한다
```

세션이 사람 입력 없이 단계를 이어 가고, 다 되면 스스로 끝을 판정한다(`Goal achieved`). 승인 창은 그대로 뜬다. 리허설에서는 part 세션에서 확인했다.

### 세션 열고 닫기
- 연다: lead와 ask는 설치 직후 바로, part는 lead가 세션 표와 뼈대를 커밋하고 띄워 달라고 할 때, check는 CONTRACT.md가 나온 뒤에 연다. 최소판 뒤 lead가 남은 요구사항으로 새 부품을 만들면 그때 또 연다.
- 켜 둔다: 맡은 일을 끝낸 세션도 켜 둔다. lead가 다음 부품을 맡기거나, 통합 중 깨진 곳을 그 세션에 고치라고 요청할 수 있다.
- 꼭 닫아야 하면(메모리 부족 등): 그 세션 '상태'에 마지막 커밋이 적혔는지 본다. 그 세션이 띄운 서버를 다른 세션이 쓰면 lead에게 넘긴 뒤 닫는다. 아니면 그 세션에 자기 서버를 끄라고 한 뒤 닫는다. 세션을 꺼도 그 세션이 띄운 서버는 남을 수 있다.
- 다시 켜면 첫 메시지로 같은 역할을 준다. work 파일을 보고 이어 간다.

## setup.sh가 하는 일

| 순서 | 대상 | 동작 |
|---|---|---|
| 0 | 작업 폴더 | README가 없으면 작업 폴더를 잘못 골랐을 수 있다고 경고 |
| 1 | `./AGENTS.md` | 없으면 복사. 있으면 기존 내용은 두고 맨 뒤에 키트 규칙을 한 번만 덧붙임. `AGENTS.override.md`가 있으면(빈 파일 포함) 키트 규칙이 적용되지 않는다고 경고. 32,768바이트를 넘어 Codex가 뒷부분을 잘라 읽게 되면 경고 |
| 2 | `./PLAN.md`, `./INTERVIEW.md`, `./DECISIONS.md`, `./CONTRACT.md`, `./work/_template.md` | 없을 때만 복사. 키트 양식과 다른 파일이 이미 있으면 덮어쓰지 않고 경고. 이름은 달라도 계획·결정·메모·약속 역할일 수 있는 문서(`TODO.md`, `TASKS.md`, `docs/plan.md` 등, 세 단계 깊이까지)가 있으면 목록을 알려 줌 |
| 3 | `./.gitignore` | 없으면 복사. 있으면 빠진 줄만 맨 앞에 넣어 기존 규칙(예외 포함)이 우선하게 함. 과제 규칙이 기록 파일(PLAN.md·INTERVIEW.md·DECISIONS.md·CONTRACT.md·work/)을 무시하면 경고 |
| 4 | `~/.agents/skills/` | 스킬 6개 복사. 같은 이름이 있으면 덮어쓰지 않고, 내용이 같은지 다른지 알려 줌. 작업 폴더부터 저장소 맨 위까지의 `.agents/skills`·`.codex/skills`와 `~/.codex/skills`에 같은 이름 스킬이 있으면 `$이름` 호출이 무시된다고 경고. 실패해도 1~3은 남음 |

인터넷 접속, sudo, `~/.codex` 수정, 파일 삭제는 하지 않는다. 기존 파일은 덮어쓰지 않고, 기존 AGENTS.md 뒤와 .gitignore 앞에 덧붙이기만 한다. 여러 번 실행해도 결과가 같다. 종료 코드는 0(완료), 1(작업 폴더 파일 설치 실패), 2(완료, 주의 사항 있음)이다.

## 스킬

`$이름`으로 부르면 Codex가 그 SKILL.md 내용 전체를 그 메시지에 붙여 보낸다(그 메시지에만 적용). 이름만 말하거나 요청이 설명과 분명히 맞거나 AGENTS.md 규칙이 가리키면 Codex가 스스로 SKILL.md를 열어 쓰기도 한다. 썼는지는 Codex가 "○○ 스킬로"라고 말하는지, Ctrl+T 기록에 그 SKILL.md를 읽은 줄이 있는지로 확인한다. 꼭 써야 하면 `$이름`으로 부른다. 같은 이름 스킬이 두 곳에 있으면 직접 친 `$이름`은 무시되므로 "SKILL.md 경로 읽고 그 절차대로 해"라고 한다.

## AGENTS.md 규칙의 근거

`공식` = 응시 환경 공식 안내, `관찰` = 사전 체험 후기, `리허설` = 이 키트로 해 본 로컬 리허설(Codex CLI 0.163, 세션 4개와 하위 에이전트). 따로 적지 않은 숫자는 1회차이고, 고친 키트로 다시 한 것은 `2회차`, 모양이 다른 과제 세 개(기존 코드 수정, 데이터 보고서, 요구가 많은 웹 시스템)로 동시에 한 것은 `11/4`, 그 수정을 180분 과제 하나(데이터 7종·규칙 판단·웹·모의 연동, 불친절한 담당자)로 확인한 것은 `검증`으로 적는다. `판단` = 작성자 판단.

| 규칙 | 근거 |
|---|---|
| README > 담당자 답 > 이 파일 | 공식: 과제 목표·필수 조건·제출물은 README 기준 |
| 세션 여러 개와 하위 에이전트로 동시에 나눠 일함 | 공식: 에이전트의 응답 시간을 고려한 위임과 시간 안배도 AI 활용 역량에 포함. 응시 환경은 터미널을 더 열 수 있음. 평가 도구 개발팀 인터뷰: 오래 걸리는 구현을 하위 에이전트에 맡기는 것을 높게 봄 |
| 파일 하나에 주인 세션 하나, 공용 파일·PLAN·CONTRACT는 lead만 | 판단: 같은 파일을 여러 세션이 동시에 고치면 서로 덮어씀 |
| 세션끼리는 work 파일 '상태'·'요청'과 CONTRACT '변경 이력'으로 맞춤 | 판단: 세션은 서로의 대화를 보지 못하고, 대화는 자동 요약되면 사라짐. 파일만 남음 |
| 세션 표의 역할은 사람이 띄우는 세션이, 하위 에이전트는 세션 안의 보조 일 | 리허설: lead가 세션 표의 부품을 하위 에이전트로 처리해 표와 실제가 달라졌고, 하위 에이전트 승인은 메인 화면에 한 줄로만 보임 |
| 답변 끝 '전달' 줄 | 리허설: 쉬는 세션은 다른 세션의 완료나 요청을 알지 못해 사람이 약 12번 말을 옮김. 한 세션이 남긴 요청 4건은 받는 세션이 끝까지 몰랐음. 2회차: 사람이 직접 지은 메시지가 4번으로 줄었지만, 전달 줄 약 36줄 중 13줄은 받는 세션이 이미 처리했거나 같은 내용이라 붙이지 않음 |
| 전달 줄은 마지막 답변 끝에, 받는 쪽에 할 일이 있을 때만 | 11/4: lead 앞 전달은 거의 다 건너뜀(18줄 중 18줄, 23줄 중 18줄). lead는 길게 한 턴으로 일하며 다른 세션 파일을 스스로 읽음. 응답 중간에 나온 전달 줄은 사람이 못 봄(한 리허설에서 7줄). 할 일 없는 확인 알림이 세션 사이를 오감. 검증: 108줄 모두 마지막 답변에 있었고 중간 0줄. 다만 ask가 담당자 답마다 4~5 세션에 '반영해 주세요'를 써서 혼자 44줄, lead 앞 줄은 대부분 'DECISIONS 커밋해 줘'라 52줄만 붙이고 56줄 건너뜀 |
| ask 전달 줄은 lead와 질문 낸 세션에만, DECISIONS.md는 덧붙인 세션이 커밋 | 검증: 위 44줄 중 다른 세션 앞 줄은 lead가 CONTRACT를 고치며 다시 알렸고, lead 앞 'D-xxx 커밋해 줘'는 모두 lead가 이미 커밋한 뒤였음 |
| 담당자 질문을 적으면 ask에 '전달' 줄 | 판단: ask는 쉬는 동안 다른 세션 work 파일에 새로 적힌 질문을 알지 못함 |
| part 이름은 기능을 나타내는 짧은 영어 단어 | 판단: 이름이 파일 이름·커밋·전달 줄에 계속 쓰이고, 사람이 이름만 보고 무슨 일인지 알아야 함. 리허설: lead가 기능 이름으로 지어 이름만 보고 알 수 있었지만, 정한 규칙은 없었음 |
| 단계 전후에는 바뀐 곳만 읽는 명령 하나 | 리허설: lead가 단계마다 기록 파일 전체를 다시 읽어 전체 토큰의 60%를 씀. 같은 결과물에서 이 명령은 전체(95KB)의 약 5분의 1만 읽음. 공식: AI 사용량은 평가에 참고될 수 있음 |
| INTERVIEW.md는 처음부터 ask | 리허설: lead가 ask가 있는 줄 모르고 INTERVIEW.md를 자기 첫 커밋에 넣으려 함 |
| lead는 답이나 화면 확인을 기다리며 멈추지 않고, 제출 시작 전 '끝났다'며 멈추지 않음 | 리허설: lead가 담당자 답을 기다리며 멈췄고, 작업 시간이 40분 넘게 남았는데 '완료'로 멈춤 |
| lead는 제출 시작 시각이나 사람 요청 때 final-check를 스스로 부르고, 그 전에는 다른 세션이 하자고 해도 시작하지 않음. 남은 요구사항이 없으면 보강할 일을 세션에 나눔 | 2회차: lead가 마감을 정리하고 "제출하면 된다"고 했지만 final-check는 사람이 불러야 했음. 11/4: 세 리허설 모두 스스로 불렀지만 제출 시작 21~51분 전에 시작해 모든 세션을 멈춤. 한 번은 다른 세션의 "최종 점검을 진행해 줘"가 계기였고, 남은 시간에 찾을 수 있던 숫자 오류가 그대로 남음. 검증: 제출 시작 전 시작 0. 다만 쉬던 lead가 00:29에 "다음은 00:30 점검"이라 하고 멈춰 사람이 깨워야 했음 |
