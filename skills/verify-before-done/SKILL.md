# 완료 전 검증

과제 구현 단계에만 쓴다. 키트 설치, 환경 확인, 도구 연습 같은 준비 작업이면 이 절차를 쓰지 않는다.

## 순서
1. PLAN.md에서 이번 단계의 '다루는 요구사항', '완료 조건', '검증' 칸과 해당 요구사항의 완료 조건을 읽고, 확인할 항목을 하나씩 나열한다.
2. 각 항목을 실제로 실행해 확인한다(AGENTS.md '검증').
   - 정상 경우
   - 요구사항·데이터 점검·담당자 답에서 나온 예외 경우 (빈 값, 중복, 제외 대상 등)
   - 기준이 있는 값의 경계 (기준 바로 아래, 같음, 바로 위)
   - 잘못된 입력 (형식이 틀린 값, 없는 파일 등)이 정해진 대로 처리되는지
   - 기대값은 구현 코드가 아닌 방법(손 계산한 작은 샘플, 담당자가 준 숫자, README 예시, 다른 방식의 계산)으로 정하고 출처를 말한다. 구현 코드 출력을 그대로 기대값으로 쓰지 않는다.
   - 방법: 테스트 실행, 스크립트 실행, 서버라면 `curl`로 응답 확인. 명령과 출력의 핵심을 보여 준다.
   - 화면이 있는 결과물이면 사람이 Browser 미리보기에서 확인할 포트, 경로, 동작을 알려 준다.
3. 다시 돌릴 수 있게 검증을 테스트 파일이나 확인 스크립트로 남긴다. README가 테스트 방식을 정하면 그것을 따른다. 앞 단계 테스트도 함께 돌려 깨진 것이 없는지 본다.
4. 실패한 항목이 있으면 원인을 찾아 고치고 같은 명령으로 다시 확인한다. 통과할 때까지 완료라고 말하지 않는다.
5. 범위 점검: 이번 변경에 '만든다'와 요구사항에 없는 기능, 설정, 추상화가 들어갔는지 본다. 있으면 빼거나, 남겨야 하는 이유를 DECISIONS.md에 적는다.
6. 기록: PLAN.md 해당 단계의 상태를 완료와 시각으로 바꾸고, '결과'에 실제 검증 출력 요약과 남은 문제를 적는다. 예상 밖 발견과 다음 할 일을 갱신한다. 이번 단계의 결정을 DECISIONS.md에 추가한다.
7. 커밋할 파일 고르기: `git status --short`로 바뀐 파일과 새 파일을 본다. 이번 단계 파일(테스트 포함)과 과제 기록 파일(PLAN.md·INTERVIEW.md·DECISIONS.md, '기록 위치'가 있으면 그 대응 파일)만 하나씩 `git add` 한다. AGENTS.md, .gitignore, `.agents/`, '시작 git 상태'의 처음부터 있던 파일, 환경 파일은 넣지 않는다(README가 요구하면 예외).
8. 보안 점검: `git diff --cached`로 스테이징한 내용 전체(새 파일 포함)를 본다. 키·토큰·비밀번호 값이 있으면 값은 출력하지 말고 파일과 행만 알린 뒤 그 내용을 빼고 다시 확인한다.
9. 커밋: "무엇: 왜" 한 줄 메시지로 커밋한다. push하지 않는다.
10. 보고: 확인한 것, 확인하지 못한 것, 다음 단계를 말한다. 다음 단계는 시작하기 전에 계획을 다시 검토한다(AGENTS.md '계획').
