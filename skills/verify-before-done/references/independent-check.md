# check 세션의 독립 검사

check 세션이 쓴다. check가 없으면 lead가 필요한 부분만 한다. AGENTS.md '검증'의 check 규칙(구현 코드와 다른 방법으로 기대값 계산, 데이터 해석마다 원본에서 반례, 결과 파일만 읽는 합격선 검사기)을 먼저 하고, 이 절차는 그 뒤를 잇는다. 검사를 늘리려고 check 세션을 더 두지 않고 하위 에이전트로 나눈다.

## 검사기 자체를 시험한다
1. 검사기는 센 대상 수(행, 사람, 규칙마다 검사한 건수)를 함께 출력한다. 대상이 0이면 '위반 0'이 아니라 '검사 안 됨'으로 실패시킨다. 종료 코드를 통과 0 / 위반 1 / 검사 안 됨 2로 나누면 다른 세션이 결과를 헷갈리지 않는다.
2. 결과 파일의 사본(제출 폴더 밖, 자기 검사 파일 안)에 규칙마다 위반을 하나씩 일부러 넣고, 그 규칙의 위반 수가 1 이상으로 나오는지 본다. 전체가 실패하는지가 아니라 그 규칙이 잡히는지를 본다. 못 잡는 규칙은 검사기를 고친다.
3. 실제 결과에서 한 번도 걸리지 않은 규칙은 걸리는 입력을 직접 만들어 구현에 넣어 본다(정해진 대로 거부·표시되는지).
4. 검사가 실패하면 먼저 검사기·표본 쪽 오류(표본을 잘못 만듦, 날짜·줄바꿈 표기 차이)인지 가른다. 검사기 오류면 고치고 '검사기 오류, 구현 결함 아님'으로 적는다.
5. 검사 결과마다 검사한 커밋(`git log -1 --format=%h`)과 시각을 적는다. 그 뒤 결과 파일이나 관련 코드가 바뀌면 다시 돌리기 전까지 옛 결과로 본다.
6. 원본 데이터는 처음과 제출 준비 전에 `sha256sum`으로 대조해 바뀌지 않았는지 본다.
7. 정의가 둘로 갈리는 지표(합친 비율과 행별 비율의 평균, 첫 검사와 재검사 반영, 분모에 미검사 포함 여부)는 두 정의로 다 계산해 차이를 보고한다. 구현과 같은 정의로 다시 계산해 맞은 것은 정확성 근거가 아니다. 차이가 크면 어느 정의인지 묻는 질문 후보를 lead에 보낸다.

## 하위 에이전트 넷
최소판이 통합된 뒤, 그리고 큰 변경이 통합될 때마다 아래 넷을 하위 에이전트로 동시에 돌린다. 과제에 맞지 않는 것은 빼고 work/check.md에 뺀 이유를 한 줄 적는다. 몇 개를 무슨 일로 띄웠는지 사람에게 알린다(AGENTS.md '세션과 역할').
- 하위 에이전트에게는 구현 대화를 넘기지 않고, 읽을 파일과 쓸 파일만 준다. 구현 과정을 모르는 눈으로 보게 하려는 것이다.
- 넷 다 제품 코드를 고치지 않는다. 쓰는 파일은 CONTRACT.md에 적힌 check 검사 파일 안에서 하위 에이전트마다 따로 나눈다.
- 테스트 명령과 서버 띄우기는 AGENTS.md '검증'대로 한다(정해진 명령 그대로, 서버 검사는 스크립트 하나로).

### 1. 경계·예외
- 입력: README, PLAN.md '요구사항', INTERVIEW.md '확정된 사실', CONTRACT.md '데이터 형식과 인터페이스', 원본 데이터. 구현 코드는 import하지 않는다.
- 할 일: 기준값마다 바로 아래·같음·바로 위, 빈 값·0·결측·중복·제외 대상, 날짜 경계(자정 넘김, 월말, 주말, 기간 양 끝), 잘못된 입력을 기대값과 그 출처와 함께 만들어 CLI·HTTP로 돌린다. 해석이 둘로 갈리는 곳은 두 해석의 결과가 달라지는 작은 입력을 하나 넣는다.
- 출력: 검사 스크립트와 결과 표(입력, 기대값과 출처, 실제, 통과·실패).
- 끝: R번호마다 경계 검사가 하나 이상이거나 '경계 없음'이 적혀 있다.

### 2. 사용자 흉내(블랙박스)
- 입력: README의 사용 방법, CONTRACT.md '실행·테스트 명령', 화면 경로와 API, `prep/pitch.md`의 데모 순서(있으면). 코드는 읽지 않는다.
- 할 일: 처음 쓰는 사람처럼 사용 방법대로 처음부터 끝까지 실행한다(명령, HTTP 요청). 역할이 여럿이면 역할마다 한다. 같은 요청 두 번, 남은 마지막 하나를 둘이 동시에, 처리 중 입력 변경처럼 여러 사람이 동시에 쓰는 경우와 서버를 다시 켠 뒤 저장이 남는지를 본다. 결과 목록의 맨 위·맨 아래 몇 건을 원본과 대조해 업무상 말이 되는지 본다. 데모 순서가 있으면 그대로 한 번 돌려 막히는 곳(빈 입력, 느린 응답, 오류)을 찾는다. 전체 실행 시간을 잰다.
- 화면: Codex는 브라우저를 열거나 조작하지 않는다. HTTP·정적 검사가 통과해도 화면 통과로 적지 않는다. 눈으로 봐야 하는 것은 '사람 확인 필요' 목록(포트, 경로, 할 동작, 기대 결과)으로 lead에게 넘긴다. 같은 화면의 확인 결과가 이미 있으면 다시 부탁하지 않는다(AGENTS.md '화면과 서버').
- 출력: 시나리오마다 통과 / 실패 / 사람 확인 필요, 실행 시간.
- 끝: README의 사용 흐름 전부를 역할마다 한 번씩 돌렸다.

### 3. 보안·취약점
- 입력: 코드와 설정(읽기만), 커밋 기록.
- 할 일: 키·토큰·비밀번호 값이 코드·커밋·로그·출력에 있는지(값은 출력하지 않고 파일과 행만), 0.0.0.0에 띄운 서버의 debug 모드, 권한을 서버에서 검사하는지(화면에서 숨기기만 했는지, id만 바꿔 남의 데이터를 읽을 수 있는지), 입력을 이어 붙인 SQL·셸 명령·파일 경로, 개인정보가 로그나 LLM 호출에 그대로 가는지, 오류 응답에 내부 경로·스택이 보이는지 본다.
- 출력: 찾은 것마다 `파일:줄`, 재현 명령, 위험, README·요구사항과의 관계.
- 끝: 위 항목마다 확인함 / 해당 없음이 적혀 있다.

### 4. 비판자
- 입력: PLAN.md '요구사항'·'비교 기록'·'결과와 한계', DECISIONS.md, work/*.md 단계 결과, `exp/비교표.md`, `prep/` 문서(있으면), 코드, 테스트 폴더의 git 기록.
- 할 일: 기록과 문서의 주장(충족, 위반 0, 개선 몇 %, 최적)마다 근거(`파일:줄`, 명령과 출력)를 찾아 확인됨 / 부분 / 어긋남 / 근거 없음으로 판정한다. 측정하지 않은 효과, fixture·mock 결과를 실제 연동이라고 한 곳, 휴리스틱 결과를 '최적'이라 한 곳을 찾는다. `git log -p -- <테스트 폴더>`에서 지워진 단언, 새로 붙은 skip, 구현 출력으로 바뀐 기대값을 찾는다. 서술형·피칭에서 찔릴 약점(약한 곳, 못 한 것, 코드와 기록이 다른 곳, 규모·동시 요청에서 깨지는 곳)을 `파일:줄 약점 → 터지면 → 다음 검증` 꼴로 한 줄씩 적는다.
- 출력: 주장 대조표, 약점 목록. 둘 다 work/check.md 그 단계 '결과'에 둔다. prep은 work 파일을 읽어 서술형 재료로 쓴다.
- 끝: 문서의 숫자와 '충족' 주장이 모두 판정됐다.

### 결과 받기
- '끝났다'는 말만 믿지 않는다. 만든 검사 파일과 출력을 보고, 그 검사 명령을 check가 직접 한 번 다시 돌려 출력이 같은지 본다. 실제로 돈 검사가 0건이거나 전부 skip이면 실패로 적는다.
- 결과마다 증거 수준을 붙인다: 실행 확인 / fixture·mock만 / 코드만 봄 / 사람 확인 필요 / 안 돌림.

## 최적화 결과
배정·일정·경로·선정처럼 제약을 지키며 무언가를 고르는 결과면:
- 결과 해를 원래 제약 전부로 다시 검사하고, 목적값을 구현과 따로 계산한다.
- 해 상태를 나눈다: 최적 입증 / 가능한 해 / 시간 초과·모름 / 불가능 증명. 시간 초과나 탐색 실패는 '모름'이지 불가능이 아니다. 배정되지 않은 대상은 배정 불가능의 증명이 아니다.
- 완전탐색이 금방 끝나는 작은 입력을 만들어 구현 결과를 최적값과 대조한다.
- 지금 방식(기준선)과 같은 입력·지표로 비교한다. 평균만 보지 않고 가장 불리한 대상(가장 많이 배정된 사람, 가장 늦게 끝나는 일)의 값도 적는다.
- 실행 시간을 적고, 솔버에 시간 제한이 걸려 있는지 본다. 방법 비교는 compare-experiments 스킬의 틀을 따른다.

## 분류·예측·이상 탐지 결과
반도체 데이터면 data-profile 스킬의 `references/semiconductor.md`(누수, 불균형 등)를 먼저 본다.
- 누수: 같은 lot·wafer·설비가 학습과 평가에 같이 들어갔는지, 운영을 흉내 내야 하면 시간 순서로 나눴는지, 결측 대치·정규화·특성 선택을 학습 구간에만 맞췄는지, 결과가 나온 뒤에야 알 수 있는 열(사후 판정, 재검사 결과)이 입력에 있는지 본다.
- 라벨을 섞어 다시 돌리면 성능이 사라지는지 본다. 사라지지 않으면 누수를 의심한다.
- 불균형: 다수 클래스만 찍는 기준선의 점수, 클래스별 재현율·정밀도, 놓친 불량 수를 함께 적는다.
- 평가 데이터는 마지막에 한 번만 쓴다. seed를 여러 개 돌려 범위를 적는다.

## 묻지 않은 조건
- 검사기는 들은 규칙만 센다. 묻지 않은 조건은 어떤 검사로도 잡히지 않는다. 결과를 보고할 때 '들은 규칙 기준'이라고 적는다.
- 검사하다가 데이터에는 있는데 어떤 규칙·답도 다루지 않는 것(쓰이지 않는 열, 규칙이 없는 대상·기간, 판정이 갈리는 경계 값)을 보면 자기 work 파일 '질문'에 담당자 질문 후보로 적고 ask에 전달한다.
- 끝까지 확인하지 못한 것은 work/check.md에 모아 둔다. lead가 final-check에서 PLAN.md '결과와 한계'로 옮긴다.

## 찾은 문제 보내기
- 원인 파일의 주인 세션(CONTRACT.md '파일 주인') 앞으로 자기 work 파일 '요청'에 적는다: `- [열림] HH:MM → <세션>: 무엇이 틀림 — 재현 명령, 기대(출처), 실제`. 받는 세션이 쉬고 있으면 답변 끝에 '전달' 줄을 쓴다(AGENTS.md '서로 맞추기').
- README·요구사항에 걸리지 않는 것(보안 권고, 요구 밖 동시 요청 처리)은 고칠지 lead가 정하게 lead 앞으로 보낸다. 요구에 없는 방어 기능을 직접 만들라고 하지 않는다. 요구 없이 넣은 장치는 과잉 설계로 감점될 수 있고, 남은 위험은 '결과와 한계'와 서술형 답으로 설명한다.
- 고쳤다는 답이 오면 같은 검사를 다시 돌려 확인한 뒤 [완료]로 바꾼다.

근거: 2차 예선 합격자 한 명은 하위 에이전트 셋으로 여러 사용자를 흉내 낸 블랙박스 검사와 취약점 점검을 따로 했고, 다른 응시자는 경계값만 보는 에이전트를 따로 돌려 결함을 더 찾았다. 하위 에이전트가 실제로는 돌지 않았는데 끝났다고 보고된 기록도 있다. 서술형은 약한 곳, 검증 방법, 동시 요청, 실행 시간을 물었다는 응시자 기록이 여럿이다. 우리 리허설에서는 check가 위반 주입과 해 상태 구분을 스스로 해 효과를 봤고, 검사기 자체 오류가 세 번 나왔으며, 들은 규칙만 센 '위반 0'이 숨은 조건 기준으로는 위반이었다. 0건 실패, 위반 주입, 판별 입력, 해 상태, 주장 대조는 여러 공개 키트에도 같은 생각이 있다(문장은 옮기지 않음).
