# 담당자 질문 후보

담당자는 업무 맥락만 답하고, 구현 방법이나 할 일 목록은 알려 주지 않는다. 질문은 사람이 직접 보낸다. 너는 후보만 만든다.

## 입력
- 과제 README와 과제 안내
- 데이터 (있으면)
- PLAN.md (있으면 '합의된 요구사항'과 '아직 열린 질문')
- 사람이 붙여 준 담당자 답 (있으면)

## 순서
1. 담당자 답이 붙어 있으면 먼저 PLAN.md '합의된 요구사항'에 반영한다. 답한 시각을 적고, 답에서 새로 드러난 조건은 따로 표시한다.
2. README에 이미 답이 있는 것은 질문으로 만들지 않는다.
3. 답에 따라 만들 것이 실제로 달라지는 불확실한 점만 고른다. 아래 순서로 빈 곳을 찾는다.
   - 맥락: 누가, 언제, 무엇을 결정하는 데 쓰나. 지금은 어떻게 처리하나
   - 사용자: 누가 보고 누가 입력하나. 권한 구분이 필요한가
   - 데이터 정의: 용어, 단위, 기간, 기준 (예: 매출은 주문 기준인가 결제 기준인가)
   - 예외: 취소, 환불, 중복, 빈 값, 테스트 데이터, 사람이 직접 결정해야 하는 경우
   - 우선순위: 시간이 부족하면 무엇부터. 이번에 안 해도 되는 것
   - 완료 기준: 어떤 상태면 됐다고 보나. 결과물 형태와 확인 방법
4. 질문 후보는 3~5개만 낸다. 각 후보는 아래 형식이다.
   - 질문: 담당자에게 보낼 한 문장. 업무 말투로, 기술 용어 없이. 가능하면 선택지를 준다.
   - 근거: README 문장이나 데이터 숫자 (예: 금액이 음수인 행 42건)
   - 답에 따라 바뀌는 것: 한 줄
5. 아직 담당자와 대화를 시작하지 않았으면 맨 앞에 "어떤 범위까지 답해 주실 수 있나요?"를 둔다.

## 합의 확인 메시지
사람이 요청하면 PLAN.md '합의된 요구사항'을 담당자에게 보낼 확인 메시지로 요약한다. 5줄 이내로 쓰고, 끝에 "이렇게 이해했는데 맞나요? 이번에 하지 않아도 되는 것도 알려 주세요."를 붙인다.

## 하지 않을 것
- "무엇을 만들면 되나요", "어떻게 구현할까요", "할 일을 알려 주세요" 같은 질문
- 후보를 한꺼번에 많이 내기
- 담당자 답을 추측해서 요구사항에 적기
