# 담당자 문답

담당자는 업무 맥락만 답하고, 구현 방법이나 할 일 목록은 알려 주지 않는다. 질문은 사람이 직접 보낸다. 너는 기록하고, 반영하고, 질문 후보를 만든다.

## 입력
- 과제 README와 과제 안내
- 데이터 (있으면)와 PLAN.md '데이터'
- INTERVIEW.md, PLAN.md '요구사항'과 '단계별 계획'
- 사람이 붙여 준 담당자 질문과 답 (있으면)

## 순서
1. 기록: 질문과 답이 붙어 있으면 INTERVIEW.md '문답 기록'에 질문 하나마다 Q번호를 붙여 원문 그대로 적는다. 요약하거나 다듬지 않는다. 시각은 사람이 알려 준 시각, 없으면 지금 한국 시간이다. 그 질문이 '물어볼 질문'에 있었으면 거기서 지운다.
2. 반영: 각 답에서 알게 된 것을 적고 PLAN.md에 반영한다.
   - 새 조건은 '요구사항'에 R번호를 붙여 추가한다. 근거에 Q번호를 적고 완료 조건을 쓴다.
   - 기존 요구사항이 바뀌면 고치고 '바뀐 기록'에 전 내용과 근거를 남긴다.
   - '목표와 범위'의 만든다·안 만든다가 바뀌면 고친다.
   - 이미 짠 단계 계획에 영향이 있으면 그 단계의 구현 내용, 완료 조건, 검증을 고친다.
   - 그 Q의 '반영' 칸에 무엇을 바꿨는지 적는다.
3. 답을 못 받은 것: 담당자가 답을 거절하거나 모른다고 하면 '답을 못 받은 것'에 옮긴다. 가정할 수 있는 후보를 적고, 사람이 고르면 DECISIONS.md에 적는다.
4. 다음 질문 찾기: README에 이미 답이 있거나 이미 물어본 것은 빼고, 답에 따라 만들 것이 실제로 달라지는 것만 고른다. 아래 순서로 빈 곳을 찾는다.
   - 맥락: 누가, 언제, 무엇을 결정하는 데 쓰나. 지금은 어떻게 처리하나
   - 사용자: 누가 보고 누가 입력하나. 권한 구분이 필요한가
   - 데이터 정의: 용어, 단위, 기간, 기준
   - 예외: 취소, 중복, 빈 값, 테스트 데이터, 사람이 직접 결정해야 하는 경우
   - 우선순위: 시간이 부족하면 무엇부터. 이번에 안 해도 되는 것
   - 완료 기준: 어떤 상태면 됐다고 보나. 결과물 형태와 확인 방법
   - 앞 답에서 새로 생긴 궁금한 점
5. 찾은 질문을 모두 INTERVIEW.md '물어볼 질문'에 결과에 영향이 큰 것부터 적는다. 형식은 "질문 — 근거(README 문장, 데이터 숫자, 앞 답) — 답에 따라 바뀌는 것"이다. 질문은 업무 말투로, 기술 용어 없이 쓰고, 가능하면 선택지를 준다.
6. 화면에는 '물어볼 질문'을 우선순위 순서로 보여 주고, 각 질문이 왜 먼저인지 한 줄씩 붙인다. 무엇을 몇 개 보낼지는 사람이 정한다.
7. 아직 담당자와 대화를 시작하지 않았으면 맨 앞에 "어떤 범위까지 답해 주실 수 있나요?"를 둔다.

## 합의 확인 메시지
사람이 요청하면 PLAN.md '목표와 범위'와 '요구사항'을 담당자에게 보낼 확인 메시지로 정리한다. 담당자가 읽기 쉽게 짧게 쓰고, 끝에 "이렇게 이해했는데 맞나요? 이번에 하지 않아도 되는 것도 알려 주세요."를 붙인다. 답을 받으면 1번부터 다시 한다.

## 하지 않을 것
- "무엇을 만들면 되나요", "어떻게 구현할까요", "할 일을 알려 주세요" 같은 질문
- 담당자 답을 추측하거나 바꿔서 기록하기
