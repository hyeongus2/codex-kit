# 서술형·피칭 준비

prep 세션이 쓴다. prep이 없으면 ask가 같은 절차로 한다. 사람이 읽고 외울 문서를 만든다. 서술형은 AI 없이, 화면을 보지 않고, 복사 없이 사람이 직접 답한다고 보고 쓴다. 피칭 질의응답도 사람이 한다. 그래서 짧고, 숫자와 근거가 분명해야 한다.

## 언제
- 시작: lead가 최소판을 통합한 뒤 "prep 세션을 켜 주세요"를 알리면 사람이 첫 메시지 `역할: prep`으로 켠다. 켜지면 바로 세 파일 초안을 만든다.
- 갱신: 사람이 "갱신해"라고 할 때, 제출 준비(final-check) 때 lead가 갱신을 전달할 때. 그때까지의 기록으로 세 파일을 다시 맞춘다.
- 사람이 "서술형 대비 요약을 만들어"라고 하면 갱신과 같다. `prep/설명.md`가 그 요약이다. `work/qa-summary.md`는 따로 만들지 않는다.
- 설명 연습과 발표 자료는 사람이 말할 때만 한다.

## 파일
- 쓰는 파일: `prep/설명.md`, `prep/서술형QnA.md`, `prep/pitch.md`, 지시받으면 `prep/slides.html`(PPT면 `prep/slides.pptx`와 만드는 스크립트 `prep/make_pptx.py`), 자기 work 파일 `work/prep.md`. 그 밖의 파일(코드, 제출물, 다른 세션 기록)은 읽기만 한다.
- 세 파일 맨 위에 `기준: 커밋 abc1234, 갱신 HH:MM(한국 시간)`을 적는다. 갱신할 때는 그 커밋 뒤로 바뀐 것부터 본다: `git log --oneline abc1234..HEAD`, `git diff --stat abc1234 HEAD`.
- `prep/`는 사람이 읽는 준비 자료이고 제출물이 아니다. 키트 .gitignore가 `prep/`를 커밋하지 않게 막는다. 커밋은 자기 기록만 한다: `git add work/prep.md && git commit -m "[prep] 무엇: 왜" -- work/prep.md`(AGENTS.md 'git'). README가 발표 자료 제출을 요구하면 그 파일만 README가 정한 곳에 따로 둔다.

## 읽는 것
- 과제 README·과제 안내: 문제, 요구, 제출물
- PLAN.md: 과제 모양, 후보 문제, 목표와 범위, 요구사항, 비교 기록, 통합 단계, 결과와 한계
- CONTRACT.md: 파일 주인(모듈 지도), 데이터 형식과 인터페이스, 실행·테스트 명령
- work/check.md: 약점 목록(`파일:줄 약점 → 터지면 → 다음 검증`), 사용자 흉내에서 막힌 곳(데모 순서에 반영)
- DECISIONS.md: 결정, 정한 사람, 사람이 한 말, 버린 대안, 방향 전환
- INTERVIEW.md: 문답 원문, 확정된 사실, 입장 표, 확인 현황, 답을 못 받은 것
- work/*.md: 단계 결과(검증 출력), 예상 밖 발견, 하위 에이전트에게 맡긴 일, 닫히지 않은 요청
- exp/비교표.md와 exp/<이름>/: 비교한 방법, 숫자, 버린 시도
- `git log --oneline`, 코드, 테스트, 검사 결과 파일. 하위 에이전트가 남긴 `결정:` 주석은 `rg -n '결정:'`으로 모은다.

읽을 것이 많으면 하위 에이전트에게 나눠 읽혀 요약을 받는다(예: 모듈 지도와 `파일:줄`, 결정·문답 정리, 숫자와 명령 모으기). 하위 에이전트는 읽기만 하고 파일은 prep이 쓴다. 테스트와 서버는 다시 돌리지 않는다. 숫자는 기록과 결과 파일에서 가져오고, 세거나 찾는 읽기 명령(`wc -l`, `rg -c`)을 썼으면 그 명령을 근거로 적는다.

## 숫자와 근거
- 숫자는 실제 파일·명령 결과에서만 쓰고, 숫자마다 근거(`파일:줄`, 또는 명령과 그 출력이 적힌 곳)를 붙인다. 찾지 못하면 '기록 없음'으로 쓴다.
- 효과는 세 가지로 나눠 적는다: `동작 확인`(돌아가고 테스트가 통과함), `주어진 자료 안의 효과`(같은 데이터로 지금 방식과 비교한 숫자), `실제 현장 효과`(현장에서 쟀다는 기록이 있을 때만). 측정하지 않은 효과(수율 몇 % 향상, 하루 몇 시간 절약)는 주장하지 않는다. 주어진 자료 안의 숫자를 현장 효과처럼 쓰지 않는다.
- 사람이 고른 이유는 DECISIONS.md '사람이 한 말'에 있을 때만 쓴다. 없으면 '기록 없음'으로 두고 사람에게 묻지 않는다. 정한 사람이 'AI 추천 채택(이유 미제시)'이면 AI가 낸 이유를 AI의 이유로 쓴다. AI가 한 일·계산을 사람이 했다고 쓰지 않는다.
- 담당자 답은 Q번호를 붙여 원문 뜻 그대로 쓴다.
- PLAN.md '데이터'의 '정의 갈림'에 있는 지표는 설명·발표·서술형 답에서 두 값과 차이, 이유를 함께 쓴다. 한 값만 쓰지 않는다.
- `파일:줄`은 쓰기 직전에 `rg -n`으로 확인하고, 갱신할 때 다시 확인한다.

## 요청
제출물(결과 파일, 제출용 문서)이나 README에 있는데 기록·코드로 설명할 수 없는 문장, 코드·결과와 다른 말, 근거 없는 효과 주장을 찾으면 고치지 않는다. work/prep.md '요청'에 `- [열림] HH:MM → lead: 파일:줄, 무엇이 왜 다른지, 근거`로 적고 답변 끝에 lead 앞 전달 줄을 쓴다(AGENTS.md '서로 맞추기'). 고쳐질 때까지 설명.md '한계'에 남기고, 서술형QnA에 그 문장을 묻는 질문을 넣는다.

## 1. prep/설명.md
항목마다 한두 줄로 쓴다. 순서:
1. 외울 숫자: 10개 안팎. `숫자 — 무엇의 숫자 — 효과 종류 — 근거`
2. 문제와 지금 방식: 누가 무엇을 어떻게 하고 있고, 무엇이 비용인가(숫자)
3. 담당자 문답에서 알아낸 것·방향을 바꾼 것: 표 `| Q번호(답한 시각) | 들은 것 | 바뀐 것(요구사항 R번호, 정의, 방법, 범위) | D번호 |`. 방향을 바꾼 답부터 쓴다(예: "Q7 재검사는 따로 집계 → 수율 정의를 바꿈"). 이어서 입장이 부딪친 것(누가 무엇을 원했나)과 고른 것·이유, 위임 답으로 둔 가정
4. 전체 흐름: 운영·사용 순서(누가 언제 무엇을 넣고 무엇을 받나), 데이터 흐름(입력 파일 → 처리 → 결과), 실행 명령
5. 모듈별 역할: 표 `| 파일 | 하는 일 | 입력 → 출력 | 만든 세션 |`
6. 방법과 고른 이유: 방법마다 무엇을 어떤 순서로 하나(그리디라면 무엇을 기준으로 무엇부터 고르나), 왜 골랐나, 버린 대안과 이유, 모든 경우를 따지지 않았다면 그 이유와 대가, 정한 사람(D번호). 방향 전환은 전 → 후, 왜, 실제 비용
7. 검증: 무엇을 어떤 명령·데이터로 확인했나, 숫자, 기대값 출처와 누가 계산했나
8. 한계와 못 한 것: 못 한 요구사항, 끝까지 묻지 못한 영역(INTERVIEW.md '확인 현황'), 가정, 닫히지 않은 요청, 들은 규칙 기준으로만 검사했다는 점
9. AI가 한 것과 사람이 정한 것: 세션·하위 에이전트가 한 일, 사람이 정한 결정(D번호와 사람이 한 말), 이유 없이 받은 AI 추천, AI가 혼자 정한 것(`결정:` 주석), AI 결과를 사람이 바로잡은 것

## 2. prep/서술형QnA.md
예상 질문과 완성된 모범 답안의 쌍이다. 모든 질문에 모범 답안을 다 적는다. 개수 상한은 없다. 기록에서 나올 수 있는 질문은 다 넣는다.

```
### Q1. 질문 [유형]
- 모범 답안: 사람이 외워 손으로 쓸 수 있는 완성된 문장 3~6줄. 숫자와 파일 이름을 넣는다
- 근거: 파일:줄, D번호, Q번호
```

가장 찔리는 질문부터 둔다: 약한 곳·못 한 것, 코드와 기록이 다른 곳, 이유가 '기록 없음'이거나 AI 추천을 그냥 받은 결정, 현장 효과로 들릴 수 있는 숫자, 방향 전환. 기록에 답이 없으면 모범 답안도 그대로 말한다(예: "확인하지 못했다. 이유는 ○○"). 약한 곳·못 한 것을 묻는 질문의 모범 답안은 '약점 위치와 조건(파일:줄) → 생기는 영향(숫자) → 다음에 확인할 방법' 순서로 쓴다.

기본 유형(해당하는 것마다 적어도 한 문항):
- 전체 운영·사용 과정, 데이터 흐름
- 담당자에게 무엇을 물었고 무엇이 바뀌었나(Q번호, 들은 것, 바뀐 것, 묻지 않았으면 무엇이 틀렸을까)
- 모듈별 설명(모듈마다)
- 알고리즘·방법 설명, 왜 그 방법인가와 대안 비교, 모든 경우를 따지지 않은 이유
- 검증 방법, 계산이 맞는지 어떻게 아나
- 조건이 바뀌면(데이터가 늘거나, 규칙·제약이 바뀌면)
- 방향 전환 이유와 비용
- 동시 요청·장애·실행 시간
- 구현한 것, 가정한 것, 못 한 것, 지금 문제점·부족한 것
- AI와 일하며 바로잡은 것
- 약한 곳, 직접 보지 않은 코드, 코드 허점

과제 맞춤: DECISIONS.md 결정마다, exp/비교표.md의 비교마다, 담당자 문답(입장 표에서 부딪친 것, 위임 답으로 둔 가정, 답을 못 받은 것), 못 한 것마다 질문을 만든다.

## 3. prep/pitch.md
말로 하므로 소리 내어 읽기 쉬운 짧은 문장으로 쓴다. 결론부터 말한다(두괄식). 숫자는 설명.md와 같은 것만 쓴다.
- 2분 판(다섯 문장, 발표 자료 2분 판의 1·2·6·8장): ① 결론: 만든 것 한 줄과 핵심 숫자 하나(예: "같은 데이터에서 놓친 불량 50 → 30건") ② 문제와 지금 비용 숫자 ③ 같은 데이터로 비교한 숫자와 확인 수준(동작 확인 / 주어진 자료 안의 효과 / 현장 효과) ④ 사람이 정한 것, AI가 한 것, 바로잡은 것 하나 ⑤ 한계와 다음 검증
- 담당자 문답에서 알아낸 것·방향을 바꾼 것: 설명.md 3번에서 두세 개를 말하는 문장으로(`Q번호: 들은 것 → 바꾼 것`). 입장이 부딪쳤으면 누구와 누구, 고른 것과 이유
- 5분 판: 발표 자료 1~9장 순서로 장마다 말할 것 2~4문장(이것이 각 장의 발표자 메모가 된다). 2분 판에 더해
  - 담당자 문답에서 알아낸 것(위 항목)
  - 접근: 입력 → 처리 → 출력, 왜 이 방법, 버린 대안 한 줄
  - 90초 데모 순서: 단계 세 개, 단계마다 보여 줄 것, 말할 것, 걸리는 시간. 멈출 수 있는 곳(서버 꺼짐, 느린 계산, 빈 입력, 오류)과 미리 막는 법(미리 띄움, 고정 입력, 미리 돌려 둔 결과 파일)
  - 검증 방법, 일부러 깨뜨려 본 시험, 한계
  - 현장에서 누가 언제 쓰나(담당자 답 근거)와 다음 단계
- 피칭 예상 Q&A: 서술형QnA와 같은 꼴로 모범 답안과 근거를 다 적는다. 상한 없음, 가장 찔리는 것부터. 바닥 목록: 상관인가 원인인가, 표본 수, 지금보다 나은 점, 현장에서 누가 언제 쓰나, 틀리면 어떻게 아나, 왜 이 접근인가, 어떻게 검증했나, 현장에 쓸 때 한계, Codex를 어떻게 썼나, 문제를 어떻게 정의했나, 담당자에게 무엇을 물었고 무엇이 바뀌었나. 과제 맞춤 질문을 더한다.
- 심사 기준 확인: OpenAI 해커톤에서 쓰인 기준으로 표를 만든다. `| 기준 | 채우는 문장·데모 | 빈 곳 |`. 기준: 문제 정의, 만든 것의 완성도, 생각의 깊이, Codex를 얼마나 잘 썼나, 짧고 일정한 데모.

## 설명 연습 (사람이 "연습하자"라고 할 때)
1. 서술형QnA와 피칭 Q&A에서 한 문항을 묻는다. `[연습: 틀림 N]` 표시가 있는 것, 찔리는 것부터 묻는다.
2. 사람이 먼저 답한다. 답을 받기 전에는 모범 답안을 보여 주지 않는다.
3. 맞은 것 / 틀린 것과 바른 내용(근거 `파일:줄`) / 빠진 것을 말한 뒤 모범 답안을 보여 준다.
4. 네다섯 문항에 하나쯤 일부러 틀린 전제를 섞는다(만들지 않은 기능, 다른 숫자, 쓰지 않은 방법). 사람이 바로잡지 못하면 틀린 전제였다고 밝히고 바른 내용을 알려 준다. 틀린 전제는 파일에 적지 않는다.
5. 틀린 문항은 서술형QnA.md 그 문항 제목 끝에 `[연습: 틀림 N]`을 달고 다음 연습에서 다시 묻는다. 맞히면 표시를 지운다.

## 발표 자료 (지시받을 때)
- 기본은 HTML 한 파일이다. 이 SKILL.md와 같은 폴더의 `assets/slides.html`(보통 `~/.agents/skills/prep/assets/slides.html`, 없으면 `/tmp/kit/skills/prep/assets/slides.html`)을 `prep/slides.html`로 복사하고, `{{…}}` 자리를 pitch.md·설명.md 내용으로 채운다. 자리 글의 쌍점 뒤는 예시다. 외부 파일·인터넷·외부 글꼴 없이 열린다. 한 장은 16:9이고 화면 크기에 맞게 커지고 작아진다.
- 장 구성(장 하나에 메시지 하나, 큰 제목 `h2`가 그 장의 한 문장). `data-short`가 붙은 1·2·6·8장이 2분 판이다.

  | 장 | 내용 |
  |---|---|
  | 1 결론 | 제목, 핵심 숫자 하나를 크게(지금 값 회색 → 새 값 강조색, 단위), 한 줄 요약, 확인 수준 |
  | 2 문제와 지금 비용 | 누가 무엇에 한 달 몇 시간·몇 건을 잃나, 숫자 카드 2~3개 |
  | 3 담당자에게서 알아낸 것 | `Q번호 들은 것 → 바꾼 것` 2~4줄(설명.md 3번), 부딪친 입장 둘과 고른 것 |
  | 4 접근 | 입력 → 처리 → 출력 상자 흐름, 왜 이 방법, 버린 대안 한 줄 |
  | 5 데모 | 단계 세 개(보여 줄 화면, 무엇을 보나, 시간), 캡처 자리(선택), 실행 한 줄 |
  | 6 같은 데이터 비교 | 지금 방식(회색) 대 새 방식(강조색) 막대, 같은 데이터의 기간·건수·판정 기준, 확인 수준 |
  | 7 어떻게 믿을 수 있나 | 검증(통과 수, 기대값 출처), 일부러 깨뜨려 본 것, 한계 |
  | 8 사람과 AI | 사람이 정한 것(문제, 지표, 맞바꿈), AI가 한 것, 바로잡은 것 하나(AI가 낸 것 → 사람이 본 문제 → 고친 결과) |
  | 9 다음 단계 | 다음 일 2~3개(누가, 언제, 무엇을 재나), 마지막 한 문장 |
  | 부록 1~4 | 상관인가 원인인가, 표본과 범위, 틀린 사례, 모듈 지도(선택). 기본은 숨김, 질의응답 때 연다 |

- 채우는 법
  - 막대(6장): `.metric`의 `data-old`(지금 방식)와 `data-new`(새 방식)에 숫자만 넣는다(쉼표는 되고 단위는 `data-unit`에). `data-better`는 작을수록 좋으면 `lower`, 클수록 좋으면 `higher`. 막대 길이와 'N% 줄어듦·늘어남'은 화면이 계산한다. 눈금을 고정하려면 `data-max`. 지표를 늘리려면 `.metric`을 복사한다. 숫자가 아니면 막대가 빗금과 '숫자 필요'로 나온다.
  - 확인 수준: 6장 `.levels`의 `data-level`에 1(동작 확인), 2(주어진 자료 안의 효과), 3(현장 효과) 중 하나를 넣는다. 설명.md의 효과 종류와 같게 하고, 현장에서 잰 기록이 없으면 3을 쓰지 않는다. 1장 칩도 같은 말로 쓴다.
  - 발표자 메모: 각 장의 `<aside class="note">`에 pitch.md 5분 판의 그 장 부분을 넣는다. 데모 장 메모에는 멈추면 대신 보여 줄 것을 넣는다. 메모는 화면에서 N 키로만 보이고 인쇄에는 나오지 않는다.
  - 캡처(5장): 사람이 준 화면 캡처나 결과 그림 파일이 있을 때만 `prep/shots/`에 두고 그 `figure` 안을 `<img src="shots/1.png" alt="무엇의 화면">`으로 바꾼다. 없으면 `figure`째 지운다. 캡처를 만들려고 브라우저를 조작하지 않는다(AGENTS.md '하지 않을 것').
  - 선택 부분: `data-optional`이 붙은 요소(비용 카드 3, 문답 줄 3, 부딪친 입장, 처리 2, 캡처, 지표 2, AI가 혼자 정한 것, 다음 일 3, 부록 4 등)는 쓸 내용이 없으면 요소째 지운다. 화면에서는 비어 있는 동안 노란 점선과 '선택' 표시가 붙는다. 선택이 아닌 자리에 쓸 내용이 없으면 '기록 없음'으로 채운다.
  - 장마다 근거 줄(`근거`)에 `파일:줄`, Q번호, D번호, 명령을 적는다. 장을 지우거나 순서를 바꾸면 머리의 장 번호(`kicker`)를 맞추고, 2분 판에 넣을 장에는 `data-short`, 부록에는 `data-appendix`를 붙인다.
- 다 채운 뒤 `rg -n -F '{{' prep/slides.html`로 남은 자리를 찾아 0줄로 만든다. 화면 위 노란 띠('채울 자리 N곳 · 이 장 M곳')도 이때 사라진다. 숫자는 설명.md '외울 숫자'와 같은지 다시 본다.
- 보는 법(사람에게 알린다): 다음은 오른쪽 화살표·스페이스·PageDown·Enter·클릭, 이전은 왼쪽 화살표·PageUp·화면 왼쪽 4분의 1 클릭, Home·End, `S` 2분 판과 전체 바꾸기, `A` 부록 보이기·숨기기, `N` 발표자 메모, `F` 전체 화면, `H` 도움말. 주소 끝에 `?short`를 붙이면 2분 판으로, `#부록`이면 부록 첫 장으로, `#6`이면 6장으로 열린다.
- PDF: 사람이 Browser에서 연 화면에서 Ctrl+P를 누르고 대상 'PDF로 저장', 여백 없음, 배경 그래픽 켜기를 고른다. 모든 장과 부록이 장마다 한 쪽(16:9 가로)으로 나오고, 메모·진행 막대·노란 띠는 나오지 않는다. 샌드박스에 `chromium`이나 `google-chrome`이 이미 있으면 `chromium --headless --print-to-pdf=prep/slides.pdf "file://$PWD/prep/slides.html"`로 만들어도 된다. 없으면 설치하지 않는다.
- 사람이 Browser에서 보려면 서버가 있어야 한다. CONTRACT.md '포트'에 prep 포트가 없으면 lead에 요청한다. `python3 -m http.server <포트> --bind 0.0.0.0 --directory prep`을 글자 그대로 백그라운드로 띄우고(작업 폴더 전체를 여는 서버를 따로 만들지 않는다) `curl`로 `/slides.html` 응답을 확인한 뒤 포트와 경로(`/slides.html`, 2분 판은 `/slides.html?short`)를 알린다. 다 보면 끈다(AGENTS.md '화면과 서버').
- 사람이 대화로 디자인(색, 글자 크기, 배치), 내용, 장 순서·추가·삭제, 형식(HTML, PDF 인쇄, 되면 PPTX)을 고쳐 달라고 하면 그대로 고친다. 고친 뒤 남은 자리 확인과 서버 응답 확인을 다시 한다. 숫자는 이때도 근거가 있는 것만 쓰고, 근거가 없으면 그 점을 말한다.
- PPTX는 사람이 원하고 `python3 -c "import pptx"`가 될 때만 만든다(.venv가 있으면 `.venv/bin/python -c "import pptx"`도 본다). 되면 `prep/make_pptx.py`로 HTML과 같은 장 구성·순서·문장·숫자로 `prep/slides.pptx`(16:9)를 만든다. 비교 막대는 지금 방식 회색, 새 방식 같은 강조색으로, 발표자 메모는 각 장의 노트에, 부록은 맨 뒤에 둔다. 안 되면 사람에게 알리고 HTML로 한다. 패키지 설치는 lead만 한다.
- 띄우는 곳과 제출 여부는 그날 안내를 따른다.
