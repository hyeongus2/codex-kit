# 제출 전 점검

새 기능은 만들지 않는다. 깨진 것을 고치는 것만 한다.

## 순서
1. 제출물 대조: README와 과제 안내에서 필수 조건과 제출물(파일 이름, 경로, 형식)을 모두 뽑아 체크리스트로 만든다. 각각 실제 파일과 실행으로 확인해 표시한다. 제출해야 할 파일이 `.gitignore`에 걸려 빠지지 않는지 `git check-ignore -v 파일`로 확인한다.
2. 최종 검증: PLAN.md에 적힌 실행·테스트 방법을 처음 보는 사람처럼 그대로 실행하고, 남겨 둔 테스트를 모두 돌려 결과를 보여 준다. 실패하거나 고친 것이 있으면 해당 검증만 다시 한다.
3. 요구사항 대조: PLAN.md '요구사항'의 R번호마다 충족·부분·미충족과 근거(검증 출력, 테스트 이름)를 정리한다.
4. PLAN.md '결과와 한계'를 채운다: 요구사항별 충족 여부, 못 한 것과 이유, 남은 위험, 더 하면 좋을 것.
5. INTERVIEW.md 정리: '물어볼 질문'에 남은 것과 '답을 못 받은 것'을 보고, 그 때문에 둔 가정을 '결과와 한계'의 남은 위험에 적는다.
6. DECISIONS.md를 정리한다: 빠진 결정을 추가하고, 근거 칸이 빈 것을 채운다.
7. 커밋 점검: `git status --short`를 PLAN.md '시작 git 상태'와 비교한다. 이번 과제로 생긴 변경과 과제 기록 파일이 모두 커밋됐는지 확인한다. 남아 있어도 되는 것은 키트 도구(AGENTS.md, .gitignore, `.agents/`)와 처음부터 있던 파일·환경 파일뿐이다. 이것들은 정리하거나 커밋하지 않는다(README가 요구하면 예외). 저장소 전체가 깨끗해야 한다는 조건은 쓰지 않는다.
8. 남은 과제 변경이 있으면 파일을 하나씩 `git add` 하고, `git diff --cached`로 키·토큰 값이 없는지 확인한 뒤 커밋한다. push하지 않는다.
9. 아래 요약을 화면에만 출력한다(파일로 만들지 않는다).
   - 핵심 결정 3개: 무엇을, 왜, 무엇을 버렸나
   - 검증 방법: 어떤 명령과 데이터로 확인했나
   - 남은 한계와 위험
   - AI에게 맡긴 것과 사람이 직접 확인하거나 결정한 것
   - 구조: 주요 파일과 각 역할
