# 제출 전 점검

lead 세션이 쓴다. 새 기능은 만들지 않는다. 깨진 것을 고치는 것만 한다.

제출 시작 시각 전이고 사람이 제출하자고 하지 않았으면 시작하지 않는다. 다른 세션이 최종 점검을 하자고 해도 같다. 그때는 AGENTS.md '시간'의 보강을 한다.

## 순서
1. 세션 마무리: 모든 work 파일의 '상태'와 '요청'을 본다. 열린 요청, 커밋 안 된 단계가 있는 세션을 찾는다. 세션마다 `전달 → <세션>: "제출 준비야. 하던 것을 검증해 커밋하고, 네 '요청'의 [열림]을 [완료]나 [못 함: 이유]로 닫고, 상태를 갱신한 뒤 멈춰"`를 쓴다. prep에는 이 줄 대신 `전달 → prep: "제출 준비야. 갱신해"`를 쓴다(prep 스킬). PLAN.md '과제 모양'에 담당자가 있으면 work/lead.md '요청'에 `- [열림] HH:MM → ask: 담당자 보고 메시지(제출 전) 초안`을 적고 ask 앞 전달 줄 끝에 "그리고 담당자 보고 메시지(제출 전) 초안을 써 줘"를 붙인다(interview-questions '보고 메시지'). 나에게 온 요청이 남았으면 처리하거나, work/lead.md '받은 요청 처리'에 못 한 이유를 적는다. 각 세션의 '상태'에 마지막 커밋이 적힐 때까지 2~8을 진행한다.
2. 제출물 대조: README와 과제 안내에서 필수 조건과 제출물(파일 이름, 경로, 형식)을 모두 뽑아 체크리스트로 만든다. 각각 실제 파일과 실행으로 확인해 표시한다. 제출해야 할 파일이 `.gitignore`에 걸려 빠지지 않는지 `git check-ignore -v 파일`로 확인한다. 반대로 `prep/`(사람이 읽는 준비 자료)는 제출물에 들어가지 않아야 한다: `git ls-files prep`이 비어 있고 `git check-ignore -v prep/설명.md`가 무시 규칙을 보여 주는지, README가 정한 제출 폴더에 prep 파일이 없는지 본다. 걸리면 사람에게 알린다. README가 발표 자료 제출을 요구하면 그 파일만 README가 정한 곳에 있는지 본다. 외부에서 데이터를 받거나 보내는 요구는 임시 DB 검사만이 아니라, 제출할 운영 상태(사람이 보는 서버와 DB)에도 실제로 반영됐는지 확인한다(예: 기준일 새 데이터가 운영 DB와 화면에 있는지).
3. 최종 검증: CONTRACT.md '실행·테스트 명령'과 PLAN.md '다음 할 일'의 실행 방법을 처음 보는 사람처럼 그대로 실행하고, 모든 세션이 남긴 테스트를 돌려 결과를 보여 준다. 합격선 지표나 지켜야 할 조건이 있으면 check의 검사기를 제출할 결과로 돌려 지표 값과 조건별 위반 수를 숫자로 보여 준다. 실제로 실행된 테스트·검사가 0건이거나 전부 skip이면 통과로 적지 않는다. 실패로 적고 왜 안 돌았는지(찾는 경로, 이름 규칙, 빠진 패키지) 확인한다. 실패하거나 고친 것이 있으면 해당 검증만 다시 한다.
4. 요구사항 대조: PLAN.md '요구사항'의 R번호마다 충족·부분·미충족과 근거(검증 출력, 테스트 이름, 맡은 세션)를 정리한다.
5. PLAN.md '결과와 한계'를 채운다: 요구사항별 충족 여부, 못 한 것과 이유, 남은 위험, 더 하면 좋을 것. INTERVIEW.md '확인 현황'에서 끝까지 일부·모름이었던 영역을 적고, '위반 0건'·'충족'은 담당자에게 들은 규칙 기준이라는 점을 함께 적는다(묻지 않은 조건은 검사하지 못했다). PLAN.md '비교 기록'이 있으면 비교마다 결과 숫자의 확인 수준(동작 확인 / 주어진 자료 안의 효과 / 실제 현장 효과)과 해 상태(최적 입증 / 가능한 해 / 시간 초과·모름 / 불가능 증명)를 그대로 옮긴다. 주어진 자료 안의 숫자를 현장 효과로 바꿔 쓰지 않는다. work 파일에 적힌 '더 하면 좋을 것'도 옮긴다. `grep -n '^- \[열림\]' work/[!_]*.md`로 닫히지 않은 요청을 찾아, 남은 것은 보낸 세션·받는 세션·내용·이유와 함께 '못 한 것과 이유'에 적는다.
6. INTERVIEW.md 정리: '다음에 보낼 질문 묶음'·'물어볼 질문'에 남은 것과 '답을 못 받은 것'을 보고, 그 때문에 둔 가정을 '결과와 한계'의 남은 위험에 적는다.
7. DECISIONS.md를 정리한다: 빠진 결정을 추가하고, 근거 칸이 빈 것을 채운다. 남이 쓴 항목은 고치지 말고 끝에 보충을 덧붙인다.
8. 커밋 점검: `git status --short`를 PLAN.md '시작 git 상태'와 비교한다. 이번 과제로 만든 파일, 과제가 준 파일 중 고친 것, 과제 기록 파일(work/<역할>.md 포함)이 모두 커밋됐는지 확인한다. 남아 있어도 되는 것은 키트 도구(AGENTS.md, .gitignore, `.agents/`, work/_template.md), 환경 파일, 고치지 않은 과제 파일뿐이다. 이것들은 정리하거나 커밋하지 않는다(README가 요구하면 예외). 저장소 전체가 깨끗해야 한다는 조건은 쓰지 않는다.
9. 남은 과제 변경이 있으면 주인 세션이 멈췄는지 확인한 뒤, 파일을 지정해 커밋한다(`git add 파일들 && git commit -m "[lead] 무엇: 왜" -- 파일들`, 한 줄). 커밋 전에 `git diff HEAD -- 파일들`(새 파일은 내용을 직접)로 키·토큰 값이 없는지 확인한다. push하지 않는다. prep 세 파일 맨 위 기준 커밋이 '결과와 한계'를 담은 커밋보다 앞이면 마지막 답변에 `전달 → prep: "결과와 한계 커밋(abc1234). 갱신해"`를 쓴다.
10. 아래 요약을 화면에만 출력한다(파일로 만들지 않는다). `prep/설명.md`가 있으면 맨 앞에 "자세한 설명과 예상 질문: prep/설명.md, prep/서술형QnA.md, prep/pitch.md(기준 커밋 abc1234)"처럼 위치를 알린다.
   - 핵심 결정 3개: 무엇을, 왜, 무엇을 버렸나
   - 부품과 세션: 어떻게 나눴고, 왜 그렇게 나눴고, 어떻게 합쳤나
   - 검증 방법: 어떤 명령과 데이터로 확인했나
   - 남은 한계와 위험(끝까지 묻지 못한 영역, 들은 규칙 기준으로만 검사했다는 점 포함)
   - AI에게 맡긴 것(세션, 하위 에이전트)과 사람이 직접 확인하거나 결정한 것
   - 구조: 주요 파일과 각 역할
